## feedback-reports

Today's feedback system (Phase 03.1-03.7) is a rich POST-MEAL REACTION report pipeline, not an ingredient-correction one. A public 6-step wizard at /feedback/new (entered via FeedbackEntryButton on restaurant + menu-item cards) collects: which menu item/dish, whether they ate there, allergens involved, staff Q&A, reaction severity (none..anaphylaxis), timing, a 1-5 trust rating, and free notes. It POSTs an idempotent (clientReportId @unique) payload to /api/v1/feedback, validated by Zod FeedbackReportInputSchema, persisting a FeedbackReport with a whitelisted minimal profile snapshot (no geolocation/raw store). Severe/anaphylaxis reports auto-create active FeedbackFlag rows (cap_restaurant_readiness, suppress_suitable, flag_for_review) plus a system audit row. Those flags are consumed by the domain recommendation engine (apply-feedback-signals.ts) to make results CONSERVATIVELY more cautious (never edits data, never upgrades to suitable) and to render a public FeedbackSummaryBanner / FeedbackUnderReviewBadge. Offline: an IndexedDB outbox (Dexie v3 pendingFeedbackReports) queues submissions when offline; useFeedbackSync drains on startup, on the offline→online edge, and via a manual "Sync now" banner, re-POSTing with submissionSource=offline_synced. Admin side is API-ONLY: list/detail/PATCH/actions routes + serializers exist (spec §10), but there is NO admin UI page (no app/admin/**/feedback page.tsx). Admin actions (start_review, dismiss, mark_spam, confirm/clear flag, suppress, downgrade, hide, request_reverification, add_note) only mutate report status + FeedbackFlag rows and always write a FeedbackAdminAction audit row — none of them edit ingredients, set a persistent traffic-light status, or record a "user contribution" provenance.

**Data model:** Prisma models FeedbackReport, FeedbackFlag, FeedbackAdminAction (migration in commit 21ffb0e). FeedbackReport is REACTION-shaped (reaction severity, reactionTiming, askedStaff/staffAnswer/staffAnswerText, userTrustRating, ateHere/visitedAt, allergenIds[], profileSnapshot json, recommendationSnapshot json, notes). FeedbackFlag is a caution OVERLAY (effect enum: flag_for_review|downgrade_confidence|suppress_suitable|cap_restaurant_readiness|hide_recommendation; status active/resolved; entityType restaurant|menu_item|dish; scoped by allergenId). GAP for v2: there is NO ingredient-level entity in this pipeline, no per-ingredient source/provenance column, and no mechanism to WRITE a corrected ingredient/traffic-light back to the menu/dish data — flags only cap/suppress recommendations, they never mutate the underlying data or stamp source=user_contribution. FeedbackEntityTypeSchema has no 'ingredient' member.
